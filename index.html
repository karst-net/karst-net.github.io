mesh vs. classic vpn

Why a mesh beats a single gateway.

A classic VPN sends everything through one doorway, wherever that doorway happens to be. A mesh lets each device talk straight to the one it needs. The difference shows up in speed, resilience, cost, and how much a single mistake can break.

THE PHYSICS, IN ONE EXAMPLE

Light in optical fibre covers roughly 200 km per millisecond, so distance sets a hard floor on latency that no hardware upgrade removes. Picture two colleagues in Frankfurt and a VPN gateway in Virginia, about 6,500 km away. A round trip between them must cross the Atlantic four times (out and back for each person), adding well over 100 ms before any processing happens. Connected directly, the same pair is limited by the distance between them — typically a few milliseconds or less. That gap is felt in every video call, SSH keystroke, file-share open, and database query.

Illustrative calculation from speed-of-light-in-fibre and great-circle distance; real routes are longer, so real hairpins are slower. Karst's own measurements are on the performance page and cover a single lab LAN only; relay-forced and multi-site paths have not been measured yet.

01

Shorter paths, lower latency

Traffic takes the direct route between peers instead of hairpinning through a central site. Nearby devices stay nearby, on the network as well as on the map.

02

No single choke point

Every conversation uses its own path, so throughput scales with the devices you add rather than with one gateway's uplink, CPU, and licence tier.

03

Redundancy built in

If one link, site, or relay fails, peers can reroute through another path instead of the whole network going dark. There is no one box whose outage takes everyone offline.

04

Graceful fallback

When NATs or firewalls block a direct connection, traffic flows through an encrypted relay. You can place relays close to your people so even the fallback path stays short.

05

Smaller blast radius

Classic VPNs often drop remote users onto a flat internal network. A mesh grants access device to device, per policy, so a compromised laptop can reach only what it was allowed to reach.

06

Less backhaul cost

Cloud-to-cloud and branch-to-branch traffic doesn't have to pass through, and be billed at, a central data centre. Fewer hops also means less bandwidth to buy and manage.

07

Grows without redesign

Adding a device means enrolling it, not re-planning tunnels, routes, and capacity at the hub. Multi-cloud, remote offices, and home labs join the same mesh the same way.

08

Control without the bottleneck

Coordination and policy live in a control plane you host yourself, while your data moves peer to peer. You keep the keys without sending every packet through your own servers.

Each one maps to a single instinct — sense, adapt, build, or secure — and a connection moves through all four in that order: Bat resolves the name, Otter finds the path, Mole fills in when Otter can't, and Raccoon has the final say on whether any of it was allowed.

Resourceful. Solves every challenge.

PHREATIC + CONTROL

PHREATIC provides the post-quantum handshake and encrypted transport. karstd runs on each client; karst-control, the admin console, and the portal handle enrollment, identity, policy, audit, relay/TURN configuration, invitations, and device lifecycle. aven · path discovery

Every connection starts on the relay. Otter spends milliseconds trying to make that temporary.

Karst doesn't wait to find the perfect path before anything works: a new connection is handed to Mole's relay immediately, and Otter starts looking for something faster in the background. It gathers every address either device might be reachable at — the device's own network interfaces, addresses other peers and relays have already observed it using, and addresses the other side reports seeing — and probes each one directly and in parallel, with small authenticated messages built for exactly this, not repurposed from something else.

Both sides probe at once, coordinated over the relay so neither one is guessing blind, and Otter keeps measuring even after a direct path is found: a path that quietly starts dropping large packets gets demoted back to the relay on its own, instead of degrading silently. The relay never goes away while this happens — Otter only ever makes a connection faster, never required for it to work. If discovery fails, is blocked, or is simply turned off, the connection just stays on Mole's relay, which is the same latency story the mesh benefits above are built on.

Path discovery decides how packets travel, never whether two devices are allowed to talk at all — that's still the ACL's call, checked on both ends, regardless of what path discovery finds. Read the AVEN spec ↗

bedrock · network lock

Adding a device isn't a database row. It's an entry in a ledger every device checks for itself.

An administrator creates a single-use invitation, scoped to one account and a specific set of access groups, shown once and good for 24 hours. Whoever receives it pastes it into setup and the client does the rest: it generates its own identity locally, verifies the server, and registers. Nobody manually edits a config file or manages a credential bundle.

What happens next depends on how the network is configured. Where Bedrock is set to enforce — a choice made in each device's own configuration, not one the server can override — the new device doesn't just start working. Setup shows Waiting for administrator approval until the new device's identity key is countersigned, often offline, on a machine with no network connection, using authority keys that can live split across hardware tokens and more than one person. That countersignature becomes one entry in a hash-chained log every device in the mesh replicates and verifies for itself — not a log the coordination server can rewrite, since it never holds the keys that sign it.

Bedrock doesn't make the server trustworthy. It makes the server unable to lie about membership without getting caught. A compromised coordination server can still deny service — drop a device from the network map, refuse an enrollment, serve a stale log — but it cannot forge a device into, or out of, the network without every other device noticing.

Being admitted to the network and being allowed to reach a given service are still two different checks — the same split Zero Trust, in plain English describes. Read the BEDROCK spec ↗

your network, your ground

Self-hosted by design.

Inside the mesh, Mole is the one that builds a hidden passage when the direct route isn't there. Self-hosting turns that same instinct outward. Run your own coordination server and relay infrastructure. Karst is built for people who want the simplicity of a modern mesh VPN without handing over the keys to their network.

That's not an invitation to trust Karst instead of your ISP or a commercial VPN vendor. We're not above being questioned about how it handles trust, and we'd rather you went looking for reasons not to than take our word for it — the security whitepaper is where we'd start.

built for the deep, built for distance

Geographic reach is something you build, not something that happens to you.

Karst has no single global network you depend on. Every region your mesh reaches is a relay you — or your organization — stood up and registered: the same job Mole does inside the mesh itself, building the passage where one doesn't already exist. Add a relay close to a cluster of people and that cluster's fallback path gets short. That's the whole mechanism.

You don't have to guess where to put the next one, or watch the evidence by hand. Relay telemetry reports back which relays clients actually use and from where — the same data behind seeing where your mesh actually lives — and the NOC map plots every relay you've located on an actual map, color-coded by health and refreshed every 30 seconds, reachable through a dedicated read-only role so a NOC watcher doesn't need admin rights just to look.

A separate Advisor process goes a step further: running continuously, it watches that same demand signal and publishes a recommendation, pool by pool, against a cost model you define — what your capacity should look like, not just what it is. It stops at recommending; acting on it is still yours to do. And because nearby peers connect directly whenever they can, most traffic never touches a relay's geography at all; see why a mesh beats a single gateway for the physics.

!
The recommendation engine is real and running. Acting on it automatically is not — yet.

ADR-0045's Scaler Advisor (Phase 1) ships today: a continuous read of recommended-versus-actual capacity per pool, against a cost model you define. What's missing is a driver that carries out its own recommendation across providers — that's Phase 2, not started, so until it lands, you're still the one who executes the change.

built-in observability

Bat doesn't just resolve names. It's how you see the mesh.

Karst exports real metrics and traces from day one, aimed at infrastructure you already run — none of it phones home to us, same as everything else in a self-hosted mesh.

⌁

01

Prometheus, from both ends

karst-control and karstd each expose their own metrics — relay registry size, Bedrock chain depth and anchor age, ACL and equivocation counters — the same numbers a support engineer sees in karst bugreport.

✦

02

Traces you turn on yourself

Point karstd or karst-control at your own OTLP collector and get spans for the handshake, the netmap push, and route reconciliation. Off by default; nothing exports until you name a collector.

03

Diagnostics that explain themselves

karst bugreport hands a support engineer the same numbers the metrics expose, labeled in plain language instead of a log dump someone has to translate.
